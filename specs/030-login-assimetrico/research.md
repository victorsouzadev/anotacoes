# Research: Login com chave assimétrica e OAuth no núcleo

- **Algoritmo**: **Decision** ES256 (P-256). Chave e assinatura pequenas, suportado nativamente no .NET e em qualquer biblioteca JWT. **Alternatives**: RS256 (funciona, tokens maiores); EdDSA (suporte irregular no `Microsoft.IdentityModel`).
- **Onde guardar a chave privada**: **Decision** arquivo PEM em `data/core/chaves/`, gerado no primeiro boot se não existir, montado só no container do núcleo. Entra no backup. **Alternatives**: no banco cifrada com o `SecretBox` (rejeitado: o banco é compartilhado com os plug-ins — 031 — então nada que permita emitir token pode ficar nele).
- **Token por plug-in**: **Decision** `POST /api/auth/token-plugin { plugin }` com o token do hub → `{ access_token, expires_in: 900 }` com `aud=<id>`. O cliente do `@grafite/ui` faz a troca e renova sozinho. **Alternatives**: um token com todas as audiências (rejeitado: um plug-in comprometido repetiria o token nos outros); cookie de sessão compartilhado (rejeitado: muda o modelo dos apps Android).
- **Transição**: **Decision** três chaves de configuração no SDK e no núcleo: `AceitarHs256Ate` (data/hora do deploy + 15 min, no núcleo), `AceitarAudienciaLegada` (plug-ins, padrão `true`), desligada por spec própria quando os APKs forem atualizados. **Alternatives**: virada única (rejeitado: derruba os apps instalados).
- **OAuth**: **Decision** portar `OAuthStore`/`OAuthEndpoints` do `cerebro` sem mudar o protocolo; o `resource` passa a ser `<base>/<id>/mcp` e o token OAuth vira um JWT ES256 com `aud=<id>` (em vez de opaco), para o plug-in validar sem consultar o núcleo. O refresh token continua opaco, em hash, no núcleo. Clientes já registrados no `hub.db` do Cérebro são migrados para `core_oauth_clientes` (033), mantendo os `client_id`.
- **Revogação imediata com JWT**: **Decision** acesso OAuth de 15 min + o plug-in consulta `GET /api/core/revogados?desde=` a cada 60 s (lista de `jti` revogados ainda não vencidos). Fica a garantia "para na próxima chamada" com atraso máximo de 60 s, registrado na spec 028 como mudança.
- **Tokens estáticos**: **Decision** tabela `core_mcp_tokens` (plug-in, hash SHA-256, e-mail, criado, último uso, revogado). O plug-in valida chamando `POST /api/core/mcp-token/validar` com cache de 5 min, ou recebe a lista de hashes ativos no mesmo endpoint de revogados. Sai o arquivo `apps-token.json`.
- **Selo das linhas de autenticação**: **Decision** coluna `Selo` = HMAC-SHA256 (chave `data/core/chaves/selo.key`, só no núcleo) sobre os campos que dão acesso: `users` (`Id`, `Email`, `PasswordHash`), `refresh_tokens` (`TokenHash`, `UserId`, `ExpiresAt`), `core_oauth_tokens` e `core_mcp_tokens` (hash, dono, plug-in, validade). Migração: no primeiro boot o núcleo sela as linhas existentes. Motivo: com o banco compartilhado (031), qualquer plug-in grava em qualquer tabela; sem o selo, inserir um refresh token seria o mesmo que forjar login. **Alternatives**: tabelas de autenticação num arquivo à parte, não montado nos plug-ins (rejeitado: o pedido é um banco só); Postgres com papéis por plug-in (ver 031, caminho de evolução).
